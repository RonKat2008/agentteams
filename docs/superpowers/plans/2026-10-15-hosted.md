# agentteams Hosted Hub (Plan 4 of 4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One hub binary can be deployed publicly (Postgres, HTTPS behind a proxy), so friends on other machines can join a team. Members prove their GitHub identity, and the orchestrator's owner grants repo access with one confirmed command.

**Architecture:**
- **Database:** the hub picks its database from config. SQLite is used for local runs. Postgres (via `pg`) is used when `DATABASE_URL` is set. PGlite is used in tests, so the whole service suite runs on both engines with no external infrastructure.
- **Hosted mode** (`AGENTTEAMS_MODE=hosted`) adds:
  - GitHub identity verification. The CLI sends the member's `gh auth token` once, at create or join time. The hub calls `GET https://api.github.com/user`, records the login, and never stores the token.
  - Rate limits and body limits.
  - A configurable Host allowlist.
- **Packaging:** a Vercel function (Hono via `hono/vercel`) plus Neon Postgres. **Deploying is not part of this plan; the controller asks the user first.**

**Tech Stack:** Node 22, TypeScript, Kysely 0.29 (`SqliteDialect`, `PostgresDialect`), `pg` 8.x, `@electric-sql/pglite` 0.5.x and `kysely-pglite-dialect` 1.3.x (tests only), Hono 4 (`hono/body-limit`), commander 15, and vitest.

**Spec:** `docs/superpowers/specs/2026-10-15-agentteams-design.md`. This plan covers:
- §3 "Collaborator access"
- §4 cross-machine mode
- §7 security: rate limits, body limits, hashed keys (already done), and GitHub tokens never stored
- §9 repository contract suite
- §10 step 5

**Deviation (ruling):** the spec says "GitHub device-flow login". Device flow needs a registered OAuth app. This plan instead verifies the user's existing `gh` token against the GitHub API once, at join. Both prove GitHub identity without the hub storing tokens. Verifying the gh token needs no app registration and no secrets on the hub. Cost if wrong: swapping in device flow later only changes how the CLI obtains the token.

## Global Constraints

- Everything in Plans 2 and 3 still applies: ESM, no keys in repo files, hooks and git hooks never wedge, idempotent installers, push after every commit.
- The hub never persists, logs or echoes a GitHub token. A token is used for exactly one `GET https://api.github.com/user` call, with a 5000 ms timeout and the headers `Accept: application/vnd.github+json`, `User-Agent: agentteams-hub`, `X-GitHub-Api-Version: 2022-11-28`, and `Authorization: Bearer <token>`.
- The CLI obtains the token with `gh auth token` only when the hub reports `mode: "hosted"`. It sends the token only to that hub over `https:` (or `http://127.0.0.1` / `http://localhost` for tests). It never prints or saves the token.
- **Hub env config:**
  - `AGENTTEAMS_MODE` is `local` (the default) or `hosted`.
  - `AGENTTEAMS_HOST` defaults to `127.0.0.1` locally; the hosted image sets `0.0.0.0`.
  - `AGENTTEAMS_PORT` defaults to 4747.
  - `DATABASE_URL`: when set, Postgres is used; otherwise SQLite at `$AGENTTEAMS_HOME/hub.db`.
  - `AGENTTEAMS_ALLOWED_HOSTS` is a comma-separated list. In hosted mode it is required, and startup fails with a clear message if it is missing. In local mode the default stays `127.0.0.1,localhost`.
- **Limits:**
  - Request bodies are limited to 64 KB, returning 413 `invalid` with message `request body too large`.
  - Authenticated requests are rate limited at 60 per minute per agent.
  - The unauthenticated `POST /api/teams`, `/api/join` and `/api/join/preview` are limited to 10 per minute per client IP. The IP comes from the first `Fly-Client-IP` or `X-Forwarded-For` entry in hosted mode only, otherwise from the socket address.
  - A limited request gets 429 with error code `rate_limited`, message `too many requests; retry in <n>s`, and a `Retry-After` header.
  - The limiters are in-memory token buckets, which is fine for a single instance. Document that.
- **Postgres transactions** run at `SERIALIZABLE` and retry up to 3 times on SQLSTATE `40001` or `40P01`, so the check-then-write races that SQLite serialises stay safe.
- A 401 from `/mcp` carries `WWW-Authenticate: Bearer realm="agentteams"`.
- `access grant` always asks for confirmation on a TTY (`Grant push access to <slug> for GitHub user <login>? [y/N]`). `--yes` skips the prompt. Without a TTY and without `--yes`, it refuses.

## Review Focus

1. **The same service suite on SQLite and PGlite.** Every existing hub test passes on both. Race tests (claims, commit dedupe, merged) must hold on Postgres semantics. (Task 1.)
2. **Hosted join from a second machine.** It must not leak the gh token in errors or logs, and the hub must reject a bad or expired token with a clear `unauthorized` message. (Tasks 3 and 4.)
3. **A hub behind Fly's proxy.** The Host allowlist must accept the public hostname, the client IP must come from `Fly-Client-IP` for rate limiting, and spoofed headers must be ignored in local mode. (Task 2.)
4. **A Codex session started while a remote hub is unreachable.** The MCP proxy must still expose tools once the hub comes back, with no restart. (Task 5.)
5. **`access grant` on a non-TTY without `--yes`** must refuse, never grant silently. (Task 4.)

- **Produces:**

- **`withTx`:** on `sqlite` it behaves as today. On `postgres` it runs `ctx.db.transaction().setIsolationLevel('serializable').execute(...)` and retries up to 3 total attempts when the error's `code` is `40001` or `40P01`. The retry waits 10 ms × attempt.

- **Test helper:**
  - The hub test helpers that create a DB read `process.env.HUB_TEST_DIALECT`. With `pglite`, they create `new PGlite()` and `new Kysely({ dialect: new PGliteDialect(pglite) })` with `dialect: 'postgres'`. Otherwise they use in-memory SQLite.
  - The root script `"test:pg": "HUB_TEST_DIALECT=pglite vitest run packages/hub"` runs the hub suite on PGlite.
- **Migrations:** they must run on Postgres unchanged, apart from a dialect-specific fix if one is needed. Plain `integer` and `text` are portable. If a migration uses SQLite-only SQL, branch on the dialect inside the migration through `db.getExecutor().adapter` or an injected flag, and document it.

**Files:**

- Modify: `packages/hub/src/db/index.ts` (lazy-load `better-sqlite3` via dynamic import so the Postgres-only function bundle never loads the native module), `packages/hub/src/http/limits.ts` (honour `x-vercel-forwarded-for` / `x-real-ip` in hosted mode), `README.md`
- Test: `packages/hub/test/vercel.test.ts`

**Requirements:**
- **`createVercelHandler()`:**
  - On a cold start it loads the config from env (hosted mode is forced). `DATABASE_URL` is required, and its absence is a clear error.
  - It creates the Postgres DB and context once per instance, and caches them in a module-level promise.
  - It returns the Hono app's fetch handler.
  - It does NOT run migrations on requests. Migrations run via `agentteams-hub-migrate`, which is run as Vercel's build command or by hand.
- **`api/index.ts`:** `export default handle(app)` via `hono/vercel`, with `export const config = { runtime: 'nodejs' }`. Route everything to it with `vercel.json` `rewrites: [{ source: '/(.*)', destination: '/api' }]`, and set `"buildCommand": "pnpm build && node packages/hub/dist/bin-migrate.js"`.
- **Allowed hosts in hosted mode on Vercel:** when `AGENTTEAMS_ALLOWED_HOSTS` is unset and `VERCEL` is `1`, default to `[VERCEL_PROJECT_PRODUCTION_URL, VERCEL_URL]`, without the scheme and with empty entries filtered out. An explicit env value overrides the default.
- **Client IP on Vercel:** in hosted mode the client IP comes from `x-vercel-forwarded-for` (first entry), then `x-real-ip`, then the existing Fly and XFF order.
- **Rate limits:** they are in-memory per function instance, so they are best-effort on serverless. Document this in the README and recommend Vercel Firewall rate-limit rules for strict limits.
- **README "Hosting a hub for friends (Vercel)":**
  1. `vercel link`.
  2. Add Neon Postgres from the Vercel Marketplace, which sets `DATABASE_URL`.
  3. `vercel env add AGENTTEAMS_ALLOWED_HOSTS`, optionally, for a custom domain.
  4. `vercel deploy --prod`.
  5. Then, for members: `agentteams create my-app --hub https://<project>.vercel.app`, friends run `agentteams join <code> --hub https://...`, and the creator runs `agentteams access grant <agent>`.
  - Security notes: HTTPS only; GitHub tokens are verified once and never stored; API keys are hashed; rate limits are best-effort per instance.
  - Keep a short "Self-hosting with Node" note: `AGENTTEAMS_MODE=hosted DATABASE_URL=... AGENTTEAMS_ALLOWED_HOSTS=... node packages/hub/dist/bin.js` behind any TLS proxy.
- **Tests:**
  - `createVercelHandler` with an injected DB (PGlite) and env: `/health` returns hosted mode.
  - The handler and DB are created once across two requests.
  - A missing `DATABASE_URL` gives a clear error.
  - The Vercel default allowed hosts are derived from `VERCEL_URL`.
  - `x-vercel-forwarded-for` is used for IP limiting in hosted mode and ignored in local mode.
  - `db/index.ts` does not import `better-sqlite3` when given a `databaseUrl`: assert this via a mock or a module-graph check.
